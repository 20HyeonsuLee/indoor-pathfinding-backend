# 시스템 아키텍처

> 전체 시스템의 구조, 서비스 간 관계, 데이터가 흐르는 방식을 설명합니다.

---

## 1. 전체 시스템 구성

이 시스템은 **3개의 독립적인 서비스**와 **1개의 공간 데이터베이스**로 구성됩니다.

```
┌─────────────────────────────────────────────────────┐
│                    클라이언트 (모바일 앱)                │
└───────────┬─────────────────────────────┬───────────┘
            │ REST API                     │ 이미지 전송
            v                              v
┌───────────────────┐          ┌───────────────────────┐
│   Spring Boot     │──호출──>│   VPS 서비스           │
│   (메인 백엔드)    │          │   (시각 위치 추정)      │
│   :8080           │          │   :5000               │
└────────┬──────────┘          └───────────────────────┘
         │
         │ 파일 업로드 / 결과 조회
         v
┌───────────────────┐
│  Python FastAPI   │
│  (경로 추출)       │
│  :8000            │
└────────┬──────────┘
         │
         v
┌───────────────────┐
│  PostgreSQL       │
│  + PostGIS        │
│  :5432            │
└───────────────────┘
```

### 각 서비스의 역할

| 서비스 | 역할 | 기술 |
|--------|------|------|
| **Spring Boot (메인)** | 모든 API의 진입점. 건물/층 관리, 길찾기, 서비스 간 조율 | Java 25, Spring Boot 4.0.2 |
| **Python FastAPI (경로 추출)** | RTAB-Map .db 파일에서 이동 경로를 추출하고 노드/엣지로 변환 | Python 3.11, FastAPI |
| **VPS (시각 위치 추정)** | 카메라 이미지를 받아 건물 내 현재 위치를 추정 | SLAM 기반 |
| **PostgreSQL + PostGIS** | 공간 데이터(좌표, 경로 기하학)를 저장하고 공간 쿼리를 지원 | PostGIS, pgRouting |

## 2. 데이터 흐름

이 시스템의 데이터는 크게 **두 가지 흐름**으로 나뉩니다.

### 흐름 A: 스캔 데이터를 경로 그래프로 변환 (관리자 흐름)

건물 관리자가 RTAB-Map으로 실내를 스캔한 뒤, 그 데이터를 시스템에 등록하는 과정입니다.

```
1. 건물/층 등록
       |
2. RTAB-Map .db 파일 업로드
       |
3. Python 서비스로 파일 전송 --> 경로 추출 시작
       |                              |
4. 상태 폴링 (진행률 확인)      <------
       |
5. 추출 결과(노드, 엣지, 세그먼트)를 DB에 저장
       |
6. POI(관심 지점) 등록 - "3층 세미나실", "1층 화장실" 등
```

**상세 과정:**

1. **업로드 단계** - 클라이언트가 .db 파일(최대 500MB)을 업로드하면, 서버는 UUID 파일명으로 저장하고 `ScanFileUploadedEvent` 도메인 이벤트를 발행합니다.

2. **추출 단계** - 이벤트 리스너가 파일을 Python 서비스에 전송합니다. Python 서비스는 비동기로 경로를 추출하며, 클라이언트는 상태를 폴링할 수 있습니다.

3. **적용 단계** - 추출이 완료되면 결과를 가져와 `PathNode`, `PathEdge`, `FloorPath` 등의 도메인 객체로 변환하여 DB에 저장합니다.

### 흐름 B: 실시간 길찾기 (사용자 흐름)

```
1. 현재 위치 파악 (VPS 또는 직접 입력)
       |
2. 목적지 검색 (POI 이름으로)
       |
3. A* 알고리즘으로 최적 경로 계산
       |
4. 턴바이턴 경로 안내 반환
   - "3m 직진 후 좌회전"
   - "엘리베이터로 2층 이동"
   - "도착: 컴공세미나실"
```

## 3. 계층 아키텍처 (DDD 기반)

Spring Boot 내부는 **도메인 주도 설계(DDD)** 원칙에 따라 계층이 분리되어 있습니다.

```
┌──────────────────────────────────┐
│  interfaces (Controller)         │  <-- HTTP 요청/응답 처리
├──────────────────────────────────┤
│  application (Service)           │  <-- 유스케이스 조율, 트랜잭션 관리
├──────────────────────────────────┤
│  domain (Model, Repository)      │  <-- 핵심 비즈니스 로직
├──────────────────────────────────┤
│  infrastructure (Client, JPA)    │  <-- 외부 시스템과의 연결
└──────────────────────────────────┘
```

### 의존성 방향

```
interfaces --> application --> domain <-- infrastructure
```

- **domain**은 어디에도 의존하지 않는 순수한 비즈니스 로직입니다.
- **infrastructure**는 domain이 정의한 인터페이스를 구현합니다.
- **application**은 domain 객체를 조합하여 유스케이스를 실행합니다.
- **interfaces**는 HTTP 요청을 application에 전달하고 응답을 변환합니다.

> 자세한 각 계층의 설계 원칙은 [기술 선택과 근거 - DDD 적용](./tech-decisions.md#3-ddd도메인-주도-설계-적용)을 참고하세요.

## 4. 도메인 모델 관계

시스템의 핵심 데이터 구조입니다.

```
Building (건물) [status: DRAFT / ACTIVE]
  ├── Floor (층)
  │     ├── FloorPath (층 경로)
  │     │     └── PathSegment (경로 조각)
  │     └── PathNode (경로 노드)
  │           └── PathEdge (노드 간 연결)
  ├── VerticalPassage (수직 이동로: 계단/엘리베이터)
  │     └── PathSegment (경로 조각)
  └── ScanSession (스캔 세션)
```

### 주요 개념

| 개념 | 설명 |
|------|------|
| **PathNode** | 경로 위의 한 점. 단순 경유지, 교차로, POI(관심지점), 층간 이동 진입/출구 등의 유형이 있음 |
| **PathEdge** | 두 노드를 잇는 연결. 수평 이동, 계단, 엘리베이터 유형을 가지며, 길찾기 선호도에 따라 가중치가 달라짐 |
| **FloorPath** | 한 층의 전체 이동 가능 경로를 LineStringZ(3D 선분)로 표현 |
| **PathSegment** | FloorPath나 VerticalPassage를 구성하는 개별 구간. 시작점과 끝점(3D)을 가짐 |
| **VerticalPassage** | 계단이나 엘리베이터 같은 층간 이동 수단. 진입점과 출구점 좌표를 가짐 |

> 각 도메인 모듈의 상세 설계는 [모듈 설계](./module-design.md)를 참고하세요.

## 5. 길찾기 알고리즘 (A*)

길찾기의 핵심은 **A* 알고리즘**입니다.

```
입력: 출발 좌표 + 목적지 이름 + 선호도(최단/엘리베이터/계단)

1. 출발 좌표에서 가장 가까운 PathNode를 찾는다
2. 목적지 이름으로 POI를 가진 PathNode를 찾는다
3. 건물 전체의 노드/엣지를 그래프로 로드한다
4. A* 알고리즘을 실행한다
   - 휴리스틱: 유클리드 거리 (3D)
   - 가중치: 선호도에 따라 엣지 비용이 달라짐
5. 결과 경로를 층 전환 기준으로 구간을 나눈다
6. 각 구간에 대해 한국어 안내 문구를 생성한다

출력: 총 거리, 예상 시간, 단계별 안내, 층 전환 정보
```

### 경로 선호도별 가중치

| 선호도 | 수평 이동 | 엘리베이터 | 계단 |
|--------|----------|-----------|------|
| 최단 거리 | 1.0x | 1.0x | 1.0x |
| 엘리베이터 선호 | 1.0x | 0.5x (할인) | 2.0x (페널티) |
| 계단 선호 | 1.0x | 2.0x (페널티) | 0.8x (할인) |

> 이 가중치 체계를 선택한 이유는 [기술 선택과 근거 - 길찾기 알고리즘](./tech-decisions.md#5-길찾기-알고리즘)을 참고하세요.

## 6. 이벤트 기반 통신

모듈 간 직접 참조를 피하기 위해 **도메인 이벤트**를 사용합니다.

```
[Scan 모듈]                      [Localization 모듈]
     |                                  |
     | ScanFileUploadedEvent 발행       |
     |--------------------------------->|
                                        |
                            RTAB-Map에서 이미지 추출
                            VPS용 데이터 준비
```

현재 사용 중인 이벤트:
- `ScanFileUploadedEvent` - 스캔 파일 업로드 완료 시 발행. RTAB-Map 이미지 추출을 트리거합니다.

> Spring의 `ApplicationEventPublisher`를 사용하며, 필요 시 `@TransactionalEventListener`로 트랜잭션과 분리합니다.

## 7. 에러 처리 전략

모든 에러는 `@RestControllerAdvice`를 통해 일관된 형식으로 반환됩니다.

```
에러 응답 형식:
{
  "code": "PF005",
  "message": "경로를 찾을 수 없습니다",
  "status": 404
}
```

에러 코드는 모듈별 접두사로 구분됩니다:
- `B` - 건물 (Building)
- `F` - 층 (Floor)
- `S` - 스캔 (Scan)
- `P` - 경로 처리 (Path Processing)
- `PF` - 길찾기 (Pathfinding)
- `V` - 위치 추정 (VPS)
- `E` - 외부 서비스 (External)

> 에러 코드 전체 목록은 소스 코드의 [`ErrorCode`](../../src/main/java/com/koreatech/indoor_pathfinding/shared/exception/ErrorCode.java)를 참고하세요.
