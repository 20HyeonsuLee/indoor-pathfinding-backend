## 작업 내용

### 백엔드 서버 구현

- DDD 기반 8개 모듈 구현: building, floor, scan, pathfinding, pathprocessing, passage, localization, shared
- 각 모듈은 domain / application / infrastructure / interfaces 4계층 구조
- 구현 중 설계 단계에서 예측하지 못한 두 가지 문제 발생

**스캔 데이터 관리 모델 변경**

- 문제: 초기 설계는 건물 단위 `ScanSession` 하나로 스캔 파일 관리
  - 실제로 스마트폰으로 한 층을 한 번에 스캔하기 어려움
  - 복도 끝에서 끊기거나, 배터리·저장공간 문제로 여러 번 나눠 스캔해야 함
- 대안 검토:
  - (1) 클라이언트에서 병합 후 업로드 → 스마트폰 연산 부담 큼
  - (2) 서버에서 청크를 받아 병합 → `rtabmap-reprocess` 도구가 서버에서만 동작
- 선택: 서버 병합
- 결과:
  - `ScanSession` → `ScanChunk`(개별 .db 파일) + `MergedScan`(병합 결과 + 상태 머신)으로 분리
  - MergedScan 상태 전이: MERGING → MERGED → EXTRACTING → COMPLETED
  - 단일 청크 선택 시 병합 건너뛰기 최적화

**비동기 처리 설계**

- 문제: 스캔 파일 병합·경로 추출에 30초~수 분 소요 → 비동기 처리 필수
- Spring 트랜잭션과 비동기 실행 간 충돌을 세 단계에 걸쳐 해결:
  - 1차 `CompletableFuture.runAsync()` → 트랜잭션 컨텍스트 밖 실행 → DB 접근 실패
  - 2차 `@Async` 별도 서비스 분리 → 트랜잭션 커밋 전 실행 → 방금 저장한 데이터 미조회
  - 3차 `MergedScanCreatedEvent` 도메인 이벤트 발행 → `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`
- 선택 이유: 메인 트랜잭션 커밋 완료 후 별도 스레드에서 실행 → DB 정합성 보장

### 노드/엣지 구성 방식의 진화

노드와 엣지를 어떻게 구성할 것인지에 대해 세 단계의 시도를 거쳤다.

**1차: 카메라 이동 경로 기반 자동 추출**

- 전제: 카메라가 지나간 경로 = 사람이 걸을 수 있는 통로
- 문제: 큰 로비에서 구석구석 스캔하면 카메라 이동 경로가 깔끔하게 나오지 않음
  - 노드/엣지 구분이 어렵고, 경로가 울퉁불퉁하게 생성됨

**2차: 포인트클라우드 2D 슬라이싱 기반 자동 추출**

- 전제: 포인트클라우드를 바닥면 기준으로 슬라이싱하면 2D 평면도가 나옴 → 여기서 노드/엣지 자동 구성
- 문제: 복도, 로비, 계단을 구분하려면 AI가 필요
  - AI는 비결정적이라 실행할 때마다 결과가 미세하게 달라짐
  - 결국 사람이 매번 수정해야 함

**3차: 포인트클라우드 위에 관리자가 직접 노드 배치 (현재 방식)**

- 발상 전환: 자동화를 포기하고, 사람이 빠르고 편하게 찍을 수 있게 하자
- 구현: 포인트클라우드를 웹에 3D로 렌더링 → 관리자가 클릭으로 노드 배치 → 엣지 연결
- 추가 문제: 3D 공간에서 클릭하면 노드가 바닥이 아닌 임의의 높이에 찍힘
  - 해결: 클릭 지점 주변 포인트클라우드의 z좌표를 분석하여 바닥면으로 보정

**포인트클라우드(PLY) 추출 파이프라인**

- RTAB-Map .db 파일은 SQLite 기반 → 웹에서 직접 렌더링 불가
- 대안 검토:
  - (1) .db에서 직접 포인트 좌표 파싱 → RTAB-Map 내부 구조 의존성 높음, 색상·법선 정보 추출 어려움
  - (2) RTAB-Map 내장 도구로 PLY 변환 → Three.js 등 웹 3D 라이브러리에서 바로 로드 가능
- 선택: PLY 변환 (표준 3D 포맷)
- 구현 흐름:
  - 병합 완료(MERGED) → `ScanProcessingExecutor`가 Python 서비스에 PLY 추출 자동 요청
  - 반환된 cache_key를 Floor 엔티티에 저장
  - `GET /api/v1/floors/{floorId}/pointcloud`로 PLY 바이트 다운로드
- 추가 이슈:
  - PLY 파일이 수십 MB → WebClient 기본 버퍼(256KB) 초과 → 메모리 오류
  - 해결: `maxInMemorySize`를 16MB로 확장

**노드/엣지 편집 API (GraphEditorController, 7개)**

- `GET /floors/{floorId}/graph` — 층 전체 그래프(노드+엣지) 조회
- `POST /floors/{floorId}/nodes` — 노드 생성 (x, y, z 좌표 + NodeType)
- `PUT /nodes/{nodeId}` — 노드 수정 (좌표 변경 시 연결된 엣지 거리 자동 재계산)
- `DELETE /nodes/{nodeId}` — 노드 삭제
- `POST /floors/{floorId}/edges` — 엣지 생성 (두 노드 연결, 양방향 여부 지정)
- `DELETE /edges/{edgeId}` — 엣지 삭제
- `DELETE /floors/{floorId}/graph` — 층 그래프 전체 초기화
- 거리 계산: 3D 유클리드 거리 자동 산출
- 엣지 타입별 A* 가중치: 수평(1.0배), 엘리베이터 우선 시 엘리베이터(0.5배)·계단(2.0배)

### 발표 PPT 제작 및 흐름 설계

- 발표 순서:
  1. 주제 선정 동기 및 타사 서비스 비교
  2. 사용 기술 설명
  3. 시연 영상 기반 완성된 서비스 설명
  4. 현재 진행 상황 공유
  5. 향후 계획 공유
